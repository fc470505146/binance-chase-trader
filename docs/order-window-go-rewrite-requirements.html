Order Window + Go 同向价追单工具重构

本页用于在正式写 Go 代码之前确认需求边界：需要维护实时 order window 数据，内置同向最优价下单工具，并把止盈止损改成本地实时价格监控触发，而不是使用 Binance 条件单。

状态：已确认核心边界 目标语言：Go 交易所：Binance USD-M Futures 剩余为实现细节选择

当前工具基线

现有 Python 版本由 daemon.py 维护 @bookTicker 实时盘口和滑动窗口，trader.py 负责下 priceMatch=QUEUE 限价单、轮询订单变化、价格变化时撤单重挂。

当前止盈止损逻辑会在成交后调用 Binance algoOrder 创建条件单；这与新需求不同，新需求要求由本地进程持续监控实时价格，触发后再发起同向价追单平仓。

重构目标

新工具建议收敛为一个 Go 长驻进程：同时管理行情、订单窗口、主动追单任务、持仓保护任务和本地状态恢复。CLI 或后续 UI 只作为控制入口，不直接承担追单循环。

实时行情 订单窗口 同向价追单 本地止盈止损 状态恢复

目标运行链路

1. Market Stream 订阅 bookTicker，维护 bid / ask / mid / age 和最近窗口。
2. Order Window 合并本地意图、交易所 open orders、成交回报和持仓快照。
3. Chase Engine 下同向最优价限价单；订单不在最优价时撤单重挂。
4. Protection Watcher 本地监控止盈止损触发价，触发后创建平仓追单任务。
5. Recovery 重启后从交易所订单、持仓和本地文件恢复未完成任务。

已确认决策

下单价格

同向价挂单买卖：BUY 走买侧排队，SELL 走卖侧排队。首版继续使用 Binance priceMatch=QUEUE，不显式传入价格。

保护单

TP/SL 暂时只支持固定价格，触发价格源使用 markPrice。数据结构预留百分比、ATR、移动止损等扩展字段。保护触发后的订单必须只用于平仓。

产品形态

首版只做 CLI + 本地长驻服务，不做图形 UI。order window 先服务于 CLI 查询、日志和状态恢复。

窗口不是只看盘口

这里的 order window 建议定义为“某个 symbol 的交易运行态视图”，不仅保存 bid/ask，也保存订单、成交、持仓和保护单的聚合状态。这样 Go 重构后可以同时支撑 CLI、日志、后续 UI 和故障恢复。

已确认窗口大小：首版按时间保留最近 60 秒，同时限制最多 1000 条 bookTicker 更新，避免极端行情下内存无界增长。

多笔订单与多套保护

首版支持同一 symbol + 同一持仓方向下存在多笔本地逻辑仓位，例如 XAGUSDT LONG 可以分三次买入，每一笔都有自己的固定 TP/SL。需要注意：Binance 交易所侧的 Hedge Mode 持仓仍是聚合持仓，本地工具负责把多笔 entry 维护成多个 ProtectionPlan。

对象 首版语义 关键字段
交易所持仓 按 symbol + positionSide 聚合，例如只有一个 XAGUSDT LONG 总持仓。 positionAmt、entryPrice、markPrice
本地逻辑仓位 每次 entry chase task 形成一条本地 plan，可拥有独立 TP/SL。 planId、entryTaskId、protectedQty、takeProfit、stopLoss
触发平仓 某个 plan 触发 TP/SL 时，只按该 plan 的 protectedQty 发起只平仓追单。 exitTaskId、triggerType、triggerPrice
并发策略 同一 symbol + positionSide 默认只允许一个开仓追单任务处于主动 chasing；已成交形成的保护 plan 可以有多个。 activeEntryTask、plans[]
设计取舍：多套保护计划是首版范围；同方向多个开仓追单同时 chasing 暂不作为默认能力。这样可以支持你分批买多并设置不同 TP/SL，同时避免两个同向追单在盘口变化时同时撤单重挂，放大限频风险。

同向最优价追单规则

动作 候选同向价 用途
BUY bestBid 买单挂在买一，偏 maker 排队。
SELL bestAsk 卖单挂在卖一，偏 maker 排队。
该项已确认：首版按 maker 同向排队价理解，不采用更激进的对手价。当前 Python 里 BUY -> ask、SELL -> bid 的比较写法不作为 Go 重写的目标语义。

订单自动切换规则

订单创建后进入 Chasing 状态。订单状态由用户数据流里的 ORDER_TRADE_UPDATE 驱动；“是否不再最优”由 bookTicker 的 bid / ask 更新驱动。两者合并后再决定是否 cancel-replace。

场景 动作
未成交，价格不再最优 撤单后用剩余数量重挂。
部分成交，价格不再最优 只对剩余数量重挂，累计成交写入窗口。
撤单失败或订单已消失 立即 reconcile，判断是成交、取消还是异常。
超过最大等待时间 按配置选择撤单退出或继续保护性追单。
结论：只靠订单订阅信息不够，因为订单事件只能告诉我们订单状态变化，不能告诉我们盘口最优价已经移动。首版应使用“行情事件触发价格检查 + 订单事件触发状态机 + 慢速 watchdog reconcile”的混合模型。

Binance 限频约束

首版需要内置本地 token bucket，并读取响应头动态降速。当前官方约束里，新订单会计入 X-MBX-ORDER-COUNT-10S 和 X-MBX-ORDER-COUNT-1M；撤单接口自身也有请求权重。服务收到 429 必须退避，持续不退避会触发 418 自动封禁。

本次查询 /fapi/v1/exchangeInfo 返回的 USD-M Futures 限频为：ORDERS 300 / 10s、ORDERS 1200 / 1m、REQUEST_WEIGHT 2400 / 1m。这些值实现时应启动读取，不写死。

项目 首版建议 原因
触发方式 行情事件驱动，但同一订单重挂需 debounce。 避免 bookTicker 高频变化导致 REST 下单风暴。
单订单最小重挂间隔 默认 1000ms，配置允许调到 500ms，不建议更低。 每次重挂至少包含撤单和新下单，且新下单计入订单限频。
全局预算 默认不超过官方订单限频的 20%，并以响应头为准动态收缩。 给手工操作、网络重试、其他工具和峰值波动留余量。
异常处理 429 立即指数退避；418 停止交易请求并报警。 避免被判断为持续违反限频。

参考：Binance USD-M Futures 官方文档的 New Order、Cancel Order、Order Update、Book Ticker Streams 和 General Info / Limits 页面。实现前仍应通过 exchangeInfo 读取实时限频配置。

本地止盈止损规则

触发方式

TP/SL 不再下 Binance 条件单，而是保存为本地 ProtectionPlan。订阅 markPrice，实时价格达到触发条件后，生成一个只平仓的 ChaseTask。

部分成交保护

一旦开仓追单出现部分成交，就按累计已成交数量创建或更新保护计划。首版只维护聚合数量，不做逐笔成交明细保护。

关键风险

本地 TP/SL 在程序退出、断网、机器休眠时不会被交易所自动执行，因此必须设计恢复、告警和可选的 failsafe。

注意：如果首版继续沿用 Hedge Mode，Binance 新订单参数里 reduceOnly 不能和 Hedge Mode 一起发送。实现上应通过 positionSide=LONG + SELL、positionSide=SHORT + BUY、数量不超过当前持仓等规则保证只平仓；如果未来支持 One-way Mode，再使用 reduceOnly=true。
持仓 TP 触发 SL 触发 触发后交易
LONG 价格大于等于 takeProfit 价格小于等于 stopLoss SELL 平多，再按同向价追单。
SHORT 价格小于等于 takeProfit 价格大于等于 stopLoss BUY 平空，再按同向价追单。
部分成交保护的首版语义：开仓任务成交 3/10 时，保护数量就是 3；后续成交到 5/10，保护数量更新为 5。若 TP/SL 被触发，先取消开仓剩余挂单，再对当前受保护数量发起只平仓追单，避免一边平仓一边继续开仓。

实现前细节选择

细节 建议首版默认 说明
CLI 命令形态 chaser serve、chaser order、chaser window、chaser protect、chaser cancel。 首版需要先把命令名和参数结构定下来，避免后续文档和实现互相牵扯。
状态文件位置 默认 ~/.binance-chase-trader/state/，支持通过配置覆盖。 需要兼容 Windows 和 Linux；状态文件不要放仓库目录，避免误提交。
配置文件格式 首版用 TOML 或 YAML 二选一；若追求 Go 标准库最少依赖，可用 JSON。 配置会承载环境、symbol 列表、限频预算、dry-run/testnet/live 等运行参数。
真实交易保护 默认 dry-run；测试网用 --testnet；实盘必须显式 --live。 工具会自动撤单重挂和平仓，实盘入口必须故意且清楚。
手工改仓处理 发现交易所持仓和本地保护数量不一致时，进入 NeedsReconcile 并暂停自动新增动作。 用户可能在 Binance 前端手工平仓或改仓，服务不能盲目按旧本地状态继续交易。
多笔同向保护的扣减规则 工具自己触发的平仓按 planId 精确扣减；外部手工减仓导致数量不一致时进入 NeedsReconcile。 交易所不会帮我们区分“这是第几笔 LONG”，本地只能对自己发出的 exit task 做确定归属。
同向开仓追单并发 默认同一 symbol + positionSide 串行开仓追单；上一笔进入 protected/done 后再允许下一笔。 既能支持多笔 LONG 保护，又能控制撤单重挂频率，首版更稳。
日志粒度 默认输出人类可读日志，同时将事件写入 JSONL。 人类日志方便盯盘，JSONL 方便恢复、排障和后续 UI 读取。

建议首版范围

  • Go 单进程服务，支持多个 symbol 的实时 order window。
  • CLI 提交开仓、平仓、取消、查询窗口。
  • 同向价 chase order，支持部分成交和自动重挂。
  • 本地 TP/SL 监控，使用 markPrice 触发，触发后走同一套 chase engine 平仓。
  • 同一 symbol + positionSide 支持多笔本地保护计划，每笔可设置不同固定 TP/SL。
  • 部分成交立即按累计已成交数量建立聚合保护；触发保护时先撤剩余开仓单，再平受保护数量。
  • 本地状态落盘和启动 reconcile，避免本地保护任务丢失。
  • 内置 Binance 限频保护，响应头接近阈值时自动降速。

暂不建议首版承诺

  • 复杂策略引擎或自动开仓信号。
  • 多交易所抽象。
  • Web Dashboard。
  • 同一 symbol + positionSide 下多个开仓追单任务同时 chasing。
  • 完全替代交易所风控。尤其是本地 TP/SL 断线风险，不能在文档里弱化。
  • 高频抢单级别的毫秒优化。首版应先保证状态正确和可恢复。

验收口径草案

类别 验收条件
Order Window 能稳定展示每个 symbol 的行情、open orders、聚合持仓、多笔保护计划、数据 age 和最近状态变化。
下单追单 下单后如果目标同向最优价变化，自动撤单并用剩余数量重挂；部分成交不会重复下已成交数量。
本地 TP/SL 触发价达到后不调用 Binance 条件单，而是按对应 plan 的受保护数量创建只平仓追单任务，并沿用同向价自动切换逻辑。
恢复 服务重启后能 reconcile 交易所 open orders 和 position，并提示缺失保护计划的持仓。
安全 所有真实下单默认需要显式确认或配置开关；提供 testnet / dry-run 模式作为首选验证路径。
