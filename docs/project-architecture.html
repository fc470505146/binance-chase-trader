运行时组件

组件 职责
CLI 进程 短命令进程。把用户命令序列化成 JSON，经本地 TCP 发给常驻服务。
Serve 进程 常驻核心。维护行情、任务、保护计划、落盘状态，并负责实际下单/撤单。
Market Stream 订阅 bookTicker 和 markPrice，驱动窗口更新、追单价格判断和 TP/SL 触发。
User Stream 订阅 ORDER_TRADE_UPDATE，驱动订单状态、部分成交、完全成交和保护计划数量更新。
Store 写快照和事件日志。服务重启后从本地状态恢复任务和保护计划。

命令链路

命令 代码入口 服务端处理
chaser serve runServe() 创建 Service，启动 control.Server，启动行情流和用户订单流。
chaser order ... runOrder() Service.SubmitEntry() 校验方向、创建 entry task、调用 placeTask()。
chaser window runSimple("window") 读取 WindowState，包含行情、任务、保护计划、最近 tick。
chaser tasks runSimple("tasks") 返回全部 ChaseTask。
chaser plans runSimple("plans") 返回全部 ProtectionPlan。
chaser cancel runCancel() 撤销本地 task；如果有交易所 orderId，则调用 Binance cancel。

核心数据模型

结构 含义
ChaseTask 一笔正在追的订单任务。可能是开仓 ENTRY，也可能是 TP/SL 触发后的平仓 EXIT。
ProtectionPlan 一笔本地逻辑仓位的保护计划。支持同一合约同方向多笔 plan，每笔有自己的固定 TP/SL。
MarketSnapshot 当前 bid、ask、mid、markPrice 和更新时间。
WindowState 面向 CLI/后续 UI 的聚合视图：行情、历史 tick、tasks、plans。
OrderUpdate 从 Binance 用户数据流解析出来的订单状态事件。

状态关系

交易所侧

Hedge Mode 下交易所只知道聚合持仓，例如 XAGUSDT LONG = 10。

本地侧

本地维护多条 ProtectionPlan：A 保护 3 张、B 保护 2 张、C 保护 5 张。某条 plan 触发时，只按这条 plan 的 protectedQty 平仓。

交易所不会告诉我们“这是第几笔 LONG”。只要用户在 Binance 前端手工改仓，本地就可能无法精确归因，因此服务会进入 NeedsReconcile / NeedsProtection，避免自动猜。

开仓追单流程

提交命令 chaser order XAGUSDT BUY 3 LONG --tp 80 --sl 76
创建任务 SubmitEntry() 创建 ENTRY task。
检查并发 同一 symbol + positionSide 已有开仓追单则拒绝。
QUEUE 下单 PlaceQueueLimit() 使用 priceMatch=QUEUE。
追单 bookTicker 变化时检查是否仍在同向最优价。
成交更新 ORDER_TRADE_UPDATE 推动 filledQty 和 plan。

本地 TP/SL 流程

阶段 代码 说明
部分成交 OnOrderUpdate() -> ensurePlanLocked() 开仓任务成交 3/10，就创建或更新一个保护 3 张的 plan。
继续成交 ensurePlanLocked() 成交到 5/10，就把同一 plan 的 protectedQty 更新为 5。
价格触发 OnMarket() -> triggerPlan() markPrice 到达固定 TP/SL，plan 进入 TRIGGERED。
撤剩余开仓 triggerPlan() 如果 entry task 还有剩余挂单，先取消它，避免一边平仓一边继续开仓。
发起平仓追单 triggerPlan() -> placeTask() 创建 EXIT task，只按该 plan 的 protectedQty 平仓。
关闭 plan OnOrderUpdate() 平仓 task 成交后，把对应 plan 标记为 CLOSED。

限频保护

configureRateLimits() 启动时读取 Binance exchangeInfo，用 CHASER_ORDER_BUDGET_RATIO 算本地 token bucket。

REST 请求后，internal/binance/client.go 会记录响应头里的 X-MBX-ORDER-COUNT-10S、X-MBX-ORDER-COUNT-1M、X-MBX-USED-WEIGHT-1M。如果接近阈值，adaptOrderBudget() 会降速。

落盘恢复

Store.Save() 写原子快照 snapshot.json；Store.Append() 追加事件到 events.jsonl。

Service.New() 启动时读取快照，恢复 markets、history、tasks、plans，并重建 client order id 和 exchange order id 索引。

改代码时的抓手

想改什么 优先看哪里 注意点
改 CLI 参数 cmd/chaser/main.go 服务端协议也可能要跟着改 internal/control。
改 TP/SL 触发规则 triggerType()、triggerPlan() 固定价格、移动止损、ATR 未来都应该先扩 ProtectionPlan。
改多笔保护归因 ensurePlanLocked()、OnOrderUpdate() 交易所侧是聚合持仓，本地只能可靠归因自己发出的 task。
改追单频率 ReplaceLimiter、TokenBucket 不要只改间隔，必须考虑 Binance 订单限频和响应头。
改状态文件格式 internal/store/store.go 要考虑旧快照兼容和崩溃时原子写入。
